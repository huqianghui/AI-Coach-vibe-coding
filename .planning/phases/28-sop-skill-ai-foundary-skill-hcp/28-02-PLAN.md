<objective>
Build the session-time skill consumption abstraction: when a session starts for a scenario
whose Skill is Foundry-synced, best-effort mount it into a Toolbox (D-02), try the real MCP
endpoint (confirmed 405 today per doc 10 §12 -- probed honestly, not hardcoded skipped, so the
path self-heals if Azure ever fixes it, per D-04), and if MCP is unavailable fall back to the
already-verified `skills.download()` + frontmatter extraction path. If the skill isn't synced
or every cloud path fails, transparently degrade to the existing Phase 19/24 local DB injection
(D-06). The returned value is the same `SkillContent` type already consumed by both text-mode
and Voice Live via `CoachingSession.focus_instruction` (D-05) -- no new Voice Live code path.

Revision note (cross-AI review, `28-REVIEWS.md`): the original plan called this abstraction on
EVERY chat message via `update_sop_progress()`, which meant a full Toolbox `create_version` +
MCP probe + ZIP `download()` -- three serial Azure network calls -- on every single user
message (HIGH-1). This revision adds a process-local TTL cache keyed on
`(skill_id, foundry_cloud_version)` inside `get_skill_content_for_session` itself, so both
`create_session()` and `update_sop_progress()` keep calling the exact same function (zero wiring
change) while the expensive cloud chain only actually runs once per skill-version per TTL
window. This same cache also partially mitigates MEDIUM-3 (unbounded Toolbox version growth --
see `<deliberate_decisions>` below) by capping `mount_skill_toolbox` calls to once per cache
window instead of once per message. MEDIUM-4 (cloud path ignoring scenario version pins) is
fixed by skipping the cloud path entirely when a scenario pins an explicit `skill_version_id`.
LOW-9 (private SDK attribute access in `_try_mcp_fetch`) is fixed with defensive `getattr` guards.

Purpose: Make skill content usable inside HCP training dialog for both text chat and Voice
Live, sourced from Foundry when possible, without ever blocking or breaking a training session,
and without regressing per-message latency versus the pre-Phase-28 local-only baseline.
Output: skill_consumption_service.py, session_service.py wired to it, unit tests.
</objective>

2. **HIGH-1 fix -- process-local TTL cache, module level, above the functions that use it:**
   ```python
   _CONTENT_CACHE_TTL_SECONDS = 600  # 10 min: long enough to absorb per-message chat traffic
   # within one training conversation, short enough that a re-publish's new foundry_cloud_version
   # (which changes the cache key) is picked up well within a single session's lifetime anyway.
   _CACHE_MISS = object()  # sentinel distinguishing "no entry" from "cached None"
   _content_cache: dict[tuple[str, str], tuple[float, SkillContent | None]] = {}

   def _cache_get(key: tuple[str, str]) -> SkillContent | None | object:
       entry = _content_cache.get(key)
       if entry is None:
           return _CACHE_MISS
       cached_at, value = entry
       if time.monotonic() - cached_at > _CONTENT_CACHE_TTL_SECONDS:
           _content_cache.pop(key, None)
           return _CACHE_MISS
       return value

   def _cache_set(key: tuple[str, str], value: SkillContent | None) -> None:
       _content_cache[key] = (time.monotonic(), value)
   ```
   This is a process-local (single-worker) cache, matching the existing single-process dev/prod
   deployment; it is intentionally NOT shared across workers/restarts -- a cold cache simply
   re-runs the cloud chain once, which is always safe (D-06 degrades cleanly either way).

## MEDIUM-3 (unbounded Toolbox version growth) — partially mitigated, residual risk accepted

**Review concern:** every `mount_skill_toolbox` call creates a new Toolbox version via
`toolboxes_op.create_version`, and nothing ever cleans these up; D-03 only deletes the *skill*
entity on archive, not toolbox versions. With no real consumer today (MCP returns 405; the
actually-used path is `download()`), mounting is described as "pure cost."

**What this revision does:** Task 1's HIGH-1 cache change means `mount_skill_toolbox` is now
called at most once per `(skill_id, foundry_cloud_version)` per `_CONTENT_CACHE_TTL_SECONDS`
(10 min) window, instead of once per chat message. This caps growth to roughly
"once per skill-version per active-session-cluster per 10 minutes" rather than "once per
message," which is an order-of-magnitude reduction but does not eliminate growth entirely --
every cache expiry across every active session still creates one more Toolbox version.

**Why full elimination is out of scope for this plan:** the review's own alternative (skip
`mount_skill_toolbox` entirely / feature-flag it off until MCP is fixed) "deviates from D-02
and needs owner confirmation" per the reviewer's own note. D-02 is a locked CONTEXT.md decision
(session-creation-time Toolbox mount) and this plan does not have authority to silently narrow
it. The cache-window mitigation above is the largest fix available without revisiting D-02.

**Residual risk:** Toolbox versions still accumulate over the lifetime of the deployment, at a
much lower rate than before this revision. This is tracked as a known cleanup item for a future
phase (e.g. an admin/ops script that prunes Toolbox versions older than N days), not blocking
Phase 28 execution. Recorded here per the phase's "either fix or document why not" rule.

## MEDIUM-7 (inline cloud sync risking 30s axios timeout) — addressed in Plan 28-01, not here

Plan 28-01 already wraps `create_from_files` in `asyncio.wait_for(..., timeout=60)` on the
