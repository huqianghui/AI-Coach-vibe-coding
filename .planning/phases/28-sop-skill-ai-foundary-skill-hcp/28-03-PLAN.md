<objective>
Expose Foundry sync state (added in Plan 28-01) through the Skill API and admin UI: schema
fields on list/detail responses, a manual retry route independent of publish, a portal-URL
discovery route, and a Skill editor status section mirroring the existing HCP agent sync UI
(`AgentStatusSection` in `agent-status-section.tsx`) -- status badge, error box, retry button,
"View in Azure Portal" link.

Purpose: Give the admin visibility and manual recovery over Foundry sync failures (D-06's
retry surface) with a UI/UX consistent with the already-established agent sync pattern (D-07).
Output: Updated schemas/routes/tests (backend), updated types/api/hooks/component/page/locales
(frontend).

Revision note (cross-AI review, `28-REVIEWS.md`): the original retry-sync guard allowed
`published` OR `archived` skills to retry, but D-03 says archiving a skill DELETES its Foundry
entity -- allowing retry on an `archived` skill would silently resurrect a cloud entity the user
intentionally removed (MEDIUM-5). This revision restricts the guard to `published` only; a
restored (→`draft`) skill must go through `publish_skill()` again to re-sync, which is already
guaranteed correct because `publish_skill()` unconditionally calls `sync_skill_to_foundry`
(Plan 28-01, D-03). The original plan also mirrored `AgentStatusSection`'s hardcoded-English
labels/toasts verbatim, which is a pre-existing, separately-tracked debt on that component --
this revision instead fully externalizes every new user-facing string (status labels, buttons,
toasts) to `en-US`/`zh-CN` locale files via `useTranslation("skill")`, matching this project's
i18n-from-day-1 requirement (MEDIUM-8), without touching `AgentStatusSection` itself.
</objective>
