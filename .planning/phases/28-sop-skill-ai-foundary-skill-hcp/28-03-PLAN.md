## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin browser → Skill API | Foundry sync status/error fields and retry/portal-url actions exposed only to authenticated admin users |
| Skill API → skill_foundry_service | Retry route triggers an outbound Entra-ID-authenticated Azure call as a direct user action |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-28-11 | Information Disclosure | `foundry_sync_error` returned in API responses | mitigate | Already truncated to 2000 chars at the source (Plan 28-01); routes are `require_role("admin")`-gated, same as all other skill mutation routes -- no new unauthenticated exposure |
| T-28-12 | Elevation of Privilege | `POST /{skill_id}/foundry-sync`, `GET /{skill_id}/foundry-portal-url` | mitigate | Both routes use the existing `Depends(require_role("admin"))` dependency identically to `publish`/`archive`/`restore` -- no new privilege surface |
| T-28-13 | Denial of Service | Admin repeatedly clicking retry-sync | accept | Each retry re-runs the already non-blocking `sync_skill_to_foundry` (Plan 28-01); frontend disables the retry button while a request is pending, bounding practical abuse to manual admin action |
| T-28-14 | Tampering | `retry_foundry_sync` route allows re-triggering sync on `published`/`archived` skills only | mitigate | Status guard (`skill.status not in ("published", "archived")` → 400) prevents retrying sync on a draft/review skill whose content may have changed post-evaluation, keeping the published-content invariant intact |
</threat_model>
